## A. 「送出日期後蒐集客戶資訊」的 bug（webhook.py）

背景：客人送出「預約 YYYY-MM-DD HH:MM」後（`webhook.py:971` booking_confirm 分支），
bot 進入逐步問答：name → birth → question（`intake_step`）。問題出在攔截層的判斷順序。

### A1.【最關鍵】問答的回答被關鍵字路由搶走，流程卡死

- **現況**：`webhook.py:836` 的 `if intent is None:` 表示「只有完全不匹配任何關鍵字的訊息」才被當成步驟回答。
  但 question 步驟的真實回答幾乎必含關鍵字：
  - 「想問**感情**」→ `category_love`、「**招財**」→ `category_wealth`、「**風水**」→ `category_fengshui`
  - 「想**問事**業發展」→ 「問事」匹配 `category_fortune`
  - 「想**預約**後再問」→ `booking`、「**服務**的部分」→ `services`、「**費用**」→ `pricing`
- **症狀**：客人回答問題 → bot 回一張不相干的分類卡片 → 資料沒存、`intake_pending` 繼續掛著 24 小時，
  之後任何不含關鍵字的訊息又被當成「姓名」重新開始問，體驗完全錯亂。這就是業主回報的主要症狀。
- **修法**：`intake_step` 存在時**反轉優先權**——先進步驟流程，只允許一個小白名單意圖跳出：
  `human`（找老師）、`payment_reported`（已匯款）、`intake_help`、管理員指令、`get_my_id`。
  其餘訊息（不論是否匹配關鍵字）一律視為當前步驟的回答；`step == "question"` 時任何文字都收。
  實作上把 `webhook.py:836` 的 `if intent is None:` 改成 `if intent not in ESCAPE_INTENTS:` 之類的白名單判斷即可。
- **測試**：intake_pending + step=question 時傳「想問感情和財運」→ 必須存為 question 並完成 intake，
  不得回 category_love 卡片。傳「已匯款」→ 必須走匯款回報。

### A2. 多行回答被誤判成「完整表單」，資料錯位

- **現況**：`_parse_intake_text`（`webhook.py:222-255`）的行分割 fallback（240-249 行）：
  任何 ≥2 行的訊息都會被拆成 name=第 1 行、birth=第 2 行 → `looks_like_intake=True`（817-818 行）→
  直接走「一次填完」路徑，**丟棄 draft**。
- **症狀**：birth 步驟客人分兩行輸入「1990年5月15日⏎早上八點」→ 姓名被覆寫成「1990年5月15日」、
  生日變成「早上八點」，前面答的姓名不見。question 步驟送多行問題 → 問題第 1 行變姓名。
- **修法**：行分割 fallback 只在 `step == "name"`（或無 step、純 intake_form 補填）時啟用；
  或要求第 2 行能被 `crm_service.parse_birth_date` 解析出日期才視為 birth。
  「1./2./3.」「姓名：」這類有明確標記的格式偵測維持不變。
- **測試**：step=birth 時傳兩行文字 → 存入 draft 的 b，姓名不變；step=question 傳多行 → 全文存為 question。

### A3. `intake_pending` 沒有在該清的地方清掉（幽靈攔截）

- **現況**，三個洞：
  1. `intent == "intake_form"`（①②③補填，`webhook.py:884-899`）存完資料**沒有**清
     `intake_pending` / `intake_step` / `intake_draft` → 之後客人說「謝謝」會被當成姓名吞掉，bot 突然問生日。
  2. `/no` 婉拒（`_cmd_booking_no`, `webhook.py:395`）刪了預約但沒清 intake 狀態 → 被婉拒的客人回「好的」，
     bot 回「收到姓名 ✓ 請回覆出生年月日時」。`/clear`（515 行）同理。
  3. 網頁後台刪預約 `/api/bookings/delete`（`api.py:174`）同樣沒清。
- **修法**：在 `state_service` 新增 `clear_intake_state(user_id)`，用一次 `_pipeline` DEL 掉
  `intake_pending / intake_step / intake_draft`（intake_data 視情境，見下），
  然後在：intake 完成的三個路徑、`/no`、`/clear`、`/api/bookings/delete` 全部呼叫。
  注意 `/no` 拿得到 `ctx_user`，`/clear` 要對每筆 entry 的 user_id 清。
- **測試**：①②③補填後傳「謝謝」→ 靜默（不被當姓名）；/no 之後傳「好的」→ 靜默。

### A4.（次要）①②③ 在 pending 期間多行輸入會存進「①」符號

`intake_pending` 攔截區在 `intent == "intake_form"` 時應直接走 ①②③ 解析（現在會先被行分割 fallback
搶走，姓名存成「①王小明」）。修法：攔截區開頭對 `intake_form` 意圖短路到既有的 ①②③ 處理（並清狀態，見 A3-1）。

## B. Notion CRM 建立失敗

### B1. 根因：integration 沒有被授權（**設定問題，老師自己做，5 分鐘**）

線上 log 是 HTTP 404，而 ID 與 schema 已驗證正確。Notion 對「integration 無權存取的頁面」一律回 404，
所以是 SPEC §5.4 的業主待辦沒完成：

1. 開 Notion → 「客户档案」「沟通记录」所在的 CRM 頁面 → 右上 `⋯` → **Connections** → 加入 bot 用的 internal integration。
   （share 父頁面一次即可，子資料庫會繼承。）
2. 確認 Vercel 的 `NOTION_API_KEY` 就是**那一個** integration 的 secret（不是別的 workspace / 別的 integration）。
3. 不需要 redeploy，設好後在 LINE 對 bot 下 `/crm` → `/crm ok` 重試佇列中保留的資料即可驗證。

### B2. 程式碼硬化（crm_service.py，防止下次沉默失敗＋資料錯亂）

1. **三態回傳**：`find_customer_by_line_id`（`crm_service.py:89`）現在把「API 失敗」和「查無此人」都回 `None`，
   `sync_booking_to_crm`（120 行）於是把 API 失敗當成新客戶去 create → Notion 恢復後會**重複建檔**。
   改成回傳三態（如 `("ok", page)` / `("not_found", None)` / `("error", None)`），
   error 時 sync 直接回失敗、佇列保留。
2. **可行動的錯誤文案**：`_post`/`_patch`（47、62 行）把 HTTP status 與 Notion 回傳的 `message` 帶回呼叫端，
   `/crm ok` 失敗時回「寫入失敗：HTTP 404 — 請確認資料庫已 share 給 integration」這類訊息，
   取代現在籠統的「客戶檔案建立/查詢失敗」。404 時直接附上 B1 的提示文字。
3. **`/paid` 的新舊客標籤查詢降級**：`webhook.py:476-478` 在 `/paid` 內同步呼叫
   `find_customer_by_line_id` 只為了在預覽卡標「新/老客戶」，Notion 掛掉時白白拖慢 webhook 最多 10 秒。
   timeout 降到 3–5 秒，失敗時標「（無法判定）」照樣出卡，不影響主流程。

驗收（沿用 SPEC §5.5 再加）：mock httpx 回 404 → `sync_booking_to_crm` 回 (False, 含 "404" 的訊息)、
不呼叫 create_customer；`/crm ok` 失敗後佇列仍在、修好後重試成功。

## C. 其他實際發生中的 bug

### C1. Calendar 刪除/更新已不存在的事件被報成失敗（log 出現 7 次）

`delete_event`（`calendar_service.py:240`）遇到 410 "Resource has been deleted"（老師手動刪過事件）回報失敗、
後台顯示錯誤。**404/410 應視為成功**（目的已達成）。`update_event` 的 404/410 則應回「事件已不存在，請確認行事曆」
這種明確訊息。用 `HttpError.status_code`（或 `resp.status`）判斷，補對應單元測試。

### C2. `/list` 編號與 `/ok` `/no` `/paid` 編號不一致，可能操作到錯的客人

`/list` 顯示的是**全部狀態**的序號，但 `/ok N` 取的是「pending 狀態中的第 N 筆」（`_pick_booking` 按狀態過濾後重新編號）。
多筆預約時老師看著 /list 的編號下 `/ok 2`，實際確認的可能是另一位客人。
修法（擇一，建議前者）：
- `/ok` `/no` `/paid` 無編號時一律先回各自的過濾清單（現行為僅多筆時顯示——維持），並在 `/list` 每行
  尾端標注該筆在對應指令下的編號，例如 `…｜⏳待確認（/ok 1）`；
- 或全部改用 /list 的全域編號。
補測試鎖定編號對應。

### C3. 同時段重複預約 race（低頻但會發生）

`booking_confirm`（`webhook.py:978`）的 `get_available_slots` 檢查與 `save_booking` 之間沒有鎖，
兩位客人同一秒選同一時段會都成功。輕量修法：`save_booking` 前
`SET slotlock:{date}:{time} {user_id} NX EX 300`，搶不到就回「這個時段剛被選走」。
